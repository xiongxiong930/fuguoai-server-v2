# 对讲 Pass3 上行 15fps 证据对账（网关侧 bin 落盘）

> 用途：给固件团队定位 B2②（上行节拍 65ms）的根因。后端侧已清白，本文只摆网关能证明的事实。

## 一、通话基本信息
- 设备 `SetIntercom start` 11:27:37 → `stop` 11:30:38（约 3 分钟）
- 手机侧 `peer='phone-Uc7d7cd08de20'`，会话正常建立+挂断
- 网关落盘路径 `/opt/fuguoai-server/data/tmp/`

## 二、bin 角色（已读 `intercom_registry.py:390/494` 确认）
| 文件 | 方向 | 含义 |
|---|---|---|
| `intercom_downlink_raw.bin` | **设备 → 网关** | 设备 mic 上行（B2 看这条） |
| `intercom_uplink_raw.bin` | 网关 → 设备 | 手机语音下行 |

bin 格式：每帧 `[4B 小端帧长 L][L 字节 payload]`，payload=`[4B 大端 seq][opus]`。**bin 内无到达时间戳**，故速率必须用「帧数 ÷ 真实通话时长」算，不能直接反推。

## 三、解码硬证据
| bin | 帧数 | 落盘时间窗 | 速率 |
|---|---|---|---|
| downlink_raw（设备→网关） | **2783** | 11:27:37→11:30:36（≈179s） | **2783÷179 ≈ 15.5 fps** |
| uplink_raw（网关→设备） | 2998 | 11:27:37→11:28:37（≈60s） | 2998÷60 ≈ **50 fps** |

- **seq 连续性**：两条 bin 均 `0 → N-1` 完全连续、**0 跳变** → 无传输丢帧（网关照单全收）。
- **opus 合法性**：`downlink_raw` opus_len avg=62.8（min17/max130），`uplink_raw` avg=60.7（min8/max104），无损坏帧。
- **下行解码 PCM 质量**：`intercom_downlink.pcm`（设备→手机解码）RMS=0.32、peak=1.0（满量程）、静音占比 17% → 真实人声送达并播放，非静音/爆音/白噪。

## 四、结论
1. **上行确为 15fps（≈65ms/帧）**：bin 帧数 ÷ 真实时长 = 15.5fps，与固件日志 `uplink alive fps=15.4` 完全吻合。这是**节奏/速率问题，不是丢帧**（seq 连续，0 丢失）。
2. **下行 50fps 真实但仅前 60s**：`uplink_raw.bin` 只落了手机讲的前 60s（2998 帧=50fps×60s），之后手机静音无下行帧。
3. **B1 喇叭修复 ✅**：下行连续+50fps（手机讲时）、`downlink.pcm` RMS 0.32/peak 满量程 → 远端音频真实送达并播放。
4. **B2 WDT 零触发 ✅**：整段 `task_wdt/panic/abort` = 0。
5. **后端清白**：下行 50fps 稳、上行帧 0 丢失 → 15fps 纯属设备侧音频任务节拍，网关只透传。根因在固件（B2②）。

## 五、给固件探针的提问（B2②）
在 `SendAudio` 内分别打：
- `ws_send` 阻塞 µs（单次 / avg / max）
- `opus` 编码 µs（单次 / avg / max）
- 每 X ms 才 flush 一次？每次 flush 带几帧？

目标：定位「音频任务为什么以 65ms 节拍跑而非 20ms」——encode 阻塞 / send 阻塞 / 与 F-1 心跳·IoT 同步帧共用同一 WS socket 串行锁 / 还是有个 65ms 定时器。修复方向：去串行化（独立发送任务 / 非阻塞 WS / 稳定 20ms 节拍）。

## 六、误区记录（避免重蹈）
- ⚠️ 早期误判"上行 50fps"是**循环论证**：用 `N×0.02s` 反推时长再得 50fps，等于假设了 20ms 间距。bin 无时间戳不能这么算。
- 速率必须经"帧数 ÷ 真实通话时长（来自 SetIntercom 起止日志）"核对。
