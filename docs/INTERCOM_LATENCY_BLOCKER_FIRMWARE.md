## 0. 结论先行

**后端侧架构已就位并把"对齐机制"修好了；现在卡住的只剩一件事：设备端音频管线端到端延迟约 4.5 秒、抖动 ±1.45 秒。**

- 但延迟 4.5s 且抖动 ±1.45s：**AEC 的时延估计每一帧都在跑，滤波器根本追不上**，数学上无法收敛。

### 1.1 为什么"杂音"是这么来的

`ref_active_rate=0.997` 表示设备下行（=手机上行）几乎恒有内容 → **环路在自持**：

```
手机说话 → 服务端 → 设备播放（延迟数秒）→ 设备 mic 拾回 → 上行 → 手机播放 → 手机 mic 拾回 → ……
```

多秒延迟下这个环**永不衰减**，手机端听到的"杂音"本质是**自己声音被延迟数秒回送的回声**（叠加谱减残留），不是设备端的人声。
（这也解释了为什么关掉 device 腿 NER 后"设备→手机有声音但全是杂音"。）

## 2. 一个很有指向性的推算：≈ 75 帧

设备上行帧实测 **60ms/帧**（`uplink_pcm_samples=960 @16k`）。

```
4500ms ÷ 60ms/帧 ≈ 75 帧
```

**这个量级是"无界队列 / 攒包未限深"的典型特征**——生产（采集/解码）快于消费（编码发送/播放取帧），队列只增不减，延迟随时间堆积到秒级，且伴随大幅抖动（消费速率波动直接变成抖动）。

> 旁证：本机 90C0 固件曾有同类问题记录——`Application::Schedule → MainLoop` 上的慢任务队列无界、
> `SendAudio` 未脱离 MainLoop，导致音频链路堆积。8818 此处表现与之一致，**建议优先按同一思路排查**。

## 3. 请贵方做的两件事

### 3.1 测量：分段量延迟（后端无法区分阶段，必须设备端测）

服务端只能测到「下行 opus 发出 → 设备 mic 捕获 → 上行回到服务端」的**总和**，无法拆开。请在设备端打点：

| 代号 | 测量区间 | 建议打点方式 |
|---|---|---|
| **T1** | 收到下行 opus → 喇叭实际出声（播放链路） | 解码输出写 I2S 前打时间戳 vs 收到包时间戳 |
| **T2** | mic 采集 → 上行 opus 离开设备（上行链路） | I2S 收满一帧打时间戳 vs 发送完成时间戳 |
| **T3（可选）** | 编码/网络发送耗时 | 单独计时，判断是否为瓶颈 |

- 端到端 ≈ **T1 + T2**，应与服务端 `delay_ms` 中位数（4493ms）对得上。
- **请把 T1 / T2 各自数值回给我们**——这直接决定改哪一侧。

> 补充线索：用户此前反馈"设备端播放还好"，**倾向于是 T2（上行攒帧）侧**；但请以实测为准。

### 3.2 修复：按嫌疑排序

**① 上行/播放队列限深（最高嫌疑）**
- 检查是否存在未设上限的 send queue / ring buffer / 待发帧链表。
- 建议：**限深 ≤ 5 帧（≤300ms）**，超出直接**丢最旧帧**（对讲场景丢帧远优于延迟堆积）。
- 确认消费侧（编码/发送、播放取帧）**按实时速率取帧**，不被 MainLoop 上其它慢任务饿死。

**② 上行不攒帧**
- 确认上行按 **20ms 或 60ms 单帧即时编码发送**，不是攒够 N 帧再发。
- 若当前为 60ms 帧，端到端预算内没问题；但**不要在其上再叠加攒包**。

**③ 播放缓冲收紧（若 T1 大）**
- 对讲场景**不要为流畅而设深 jitter buffer**。建议播放缓冲 ≤ 100ms，宁可丢帧/补静音也不要深缓冲。

**④ 发送路径脱离 MainLoop（若 T3 大 / 消费被饿死）**
- 编码与发送移到独立高优先级任务（参考 90C0 的 `SendAudio 脱离 MainLoop` 改法），
- 避免与 UI/网络等慢任务共享同一队列被阻塞。

## 7. 一个诚实的说明（避免我们被自己的数据误导）

4.5s 这个数来自互相关时延估计。**自持环路产生的周期性啸叫音，会在多个时延点产生伪峰**（周期信号在非真实滞后处也能拿到高相关，`corr max=0.862` 不能 100% 排除伪峰可能）。

因此：
- 我们**不以 4.5s 作为定论**，而是作为**强指向性线索**（配合 90C0 同类问题、用户"播放还好"反馈、以及环路自持现象，指向性很强）。
- **请以 §3.1 的设备端直测 T1/T2 为准**。若直测显示各段都很快（比如总共 <100ms），那说明是伪峰，请回给我们，我们改从"AEC 参考/对齐"方向重查，不再纠缠延迟。
