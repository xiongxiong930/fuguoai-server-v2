## 0. 验收边界（必须先读）

"真机验收"分两层，本环境当前只能完整覆盖**第一层**：

| 层 | 内容 | 谁来做 | 本环境能否验 |
|---|---|---|---|
| **A. 服务端逻辑验收** | 人格/记忆/家庭RAG/eval/工具容错 的真实代码路径、配置开关、磁盘持久化、live `/metrics` 端点 | 本探针（容器内跑真实部署代码） | ✅ 能 |
| **B. 物理设备对话验收** | 真实设备 WS 接入→对话→人格生效/记忆召回/家庭事实注入/评分点亮→出声 | **需你上真机** | ⏸️ 手动 |

判定"**超越初始版本**"必须有 B 层的实测证据（真机对话里人格/记忆/家庭事实确实被注入、eval 指标确实跳动）。
A 层通过只是"代码正确、可部署"，不等于"已被证明显著更聪明"。

## 1. 各维度验收标准与证据

### 维度② — 长期记忆 + 人格

## 3. 重要发现 — M16 验证器注入状态（2026-07-30 实测更正）

> ⚠️ **本节为更正**：早版报告曾写"159 未注入 M16 用户验证器→管理 API 401"，**该结论错误**，
> 实为服务端探针 `acceptance_probe.py` 未携带 JWT 直打所致。以下为 159 容器内端到端实测结果。

实测方式（`probe_m16_injection.py`，容器内直连 `127.0.0.1:8002`，用同容器 config.yaml 的
`jwt_secret` mint token，与线上进程同密钥）：

| 调用 | 结果 | 说明 |
|---|---|---|
| `verify_mini_program_user(有效token)` | `dict`（非 None） | 验证器逻辑正常 |
| `GET /api/v1/auth/me`（带 token） | **200** | 守卫放行，返回 `user_id/openid` |
| `GET /api/v1/persona/probe-device`（带 token） | **404**（body: 设备不存在或无权访问） | **非 401**——守卫已过，404 是设备归属校验（probe 设备未绑定该用户） |
| `GET /api/v1/family-knowledge/probe-device`（带 token） | **404** | 同上 |

结论：
- **M16 用户验证器已注入并工作**（注入点 `fuguoai_core/api/auth_routes.py:25` 在 `http_server.py:469 apply_routes()` 启动路径中被触发；线上 159 容器文件已部署、events WS 握手放行亦佐证）。
- 管理 API **不会 401**；返回 404 仅因设备未绑定到该用户（`persona_routes._resolve` 的归属校验，正确行为，不泄露设备存在性）。
- JWT 密钥取自 `config.yaml miniprogram.jwt_secret`（已配置、稳定），非环境变量 `FUGUOAI_JWT_SECRET`（该 env 为空，但 config 兜底生效），重启不会使旧 token 失效。
- **管理页真正打通的钥匙 = 设备绑定**：`handle_bind_token` 把 bind_token 绑到小程序 uid，`handle_bind` 绑定设备时 `set_status(device, active, user_id=rec["user_id"])`，归属正确落到用户；绑定后 `GET /persona/{device}` 即返回 200。
- 这不阻塞"自进化能力生效"——`chat()` 直接复用 `PersonaStore` / `FamilyRAG` 数据层，**无需走 HTTP API**。

设备 `espreal01` 当前不在线，改用**数据层直验**：在 159 容器内直接调 `PersonaStore` / `FamilyRAG` / `DialogueEval` 单例（与服务同 config），复刻 `connection.py:1526-1550` 注入逻辑，eval 用 mock judge（不触发真实 LLM）。脚本 `datalayer_verify.py`。

### 结果

| 维度 | 验证项 | 结果 |
|---|---|---|
| ② persona | `persona.enabled=True`；`render(espreal01)` 产出 `<persona>` 块（name=复果, style=温暖简洁自然口语） | ✅ 真实生效 |
| ④ eval | `dialogue_eval.enabled=True`；mock judge 跑 `evaluate()` → `fuguoai_eval_total` 0→1（计数递增）、`fuguoai_eval_last_overall gauge=5.0` | ✅ 闭环工作 |
| ⑤ family RAG | **存储/写入/清理管道 ✅**（upsert→retrieve→render→remove 全通）；**字面重叠 query 正确检索并注入 `<family_knowledge>`** | ✅ 管道通 |
| ⑤ family RAG | **默认 `local` 嵌入语义深度不足 ⚠️**：自然问句「我有什么忌口」「我对什么过敏」与陈述事实「用户不吃香菜和海鲜」字面零重叠 → 余弦相似度 0 → 不检索、不注入 | ⚠️ 局限 |

### 关键发现：维度⑤ 的检索质量受默认嵌入限制

- `config.yaml`(运行配置 `data/.config.yaml` 第 1216 行) `FamilyRAG.embedding.type: local`。
- `LocalHashEmbedding` 是**纯词面 TF-IDF**（字符+bigram 哈希到 512 维，L2 归一化），docstring 自承"语义能力有限；配置 OpenAIEmbedding 即升级真语义"。
- 实测：字面重叠 query（"香菜和海鲜""不吃海鲜"）→ 正确检索注入；自然问句（"我有什么忌口""我对什么过敏"）→ 0 相似 → 不注入。
- **结论**：维度⑤ 的"录入/存储/注入"全链路正确可用；但**默认配置下家庭知识只对字面命中生效，无法应对自然语言的转述/提问**，对真实用户体验等于"基本不可用"。
- **修复方向（待你拍板，属产品决策+可能需联网/下载模型，不擅自改）**：
  - A. 配 `OpenAIEmbedding`（text-embedding 模型，需 API key + 设备联网）；
  - B. 换本地 sentence-transformer 嵌入（离线可用，需下载模型 ~20-90MB + torch）。

### eval 计数验证细节

- `evaluate()` 走 `_JUDGE_EXECUTOR` 线程池 + `asyncio.wait_for(timeout)` 熔断（与 `connection.py:1838 evaluate_async` 一致）；
- 用 `_set_test_llm(mock)` 注入确定性 judge，证明 `fuguoai_eval_total` 真实 +1、`fuguoai_eval_last_overall` gauge 被正确设置；
- 生产环境真实 judge LLM 配置块需存在（否则 `evaluate` 静默返回 None、不计数）——需在真机 /metrics 复核 `fuguoai_eval_total>0`。
